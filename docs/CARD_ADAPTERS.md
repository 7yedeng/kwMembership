# 可替换卡台适配层

更新：2026-11-14。本文描述代码接口及离线验证，不表示已登录任何卡台、开卡、充值或支付。

## 责任边界

`Processor` 继续管理共享 kwRedeem SQLite 中的订单、库存、账户锁、资金许可与对账。它从 `membership_card_platforms` 读取配置并使用共享 `JWT_SECRET` 解密凭据，然后调用 `provider.NewCardPlatform`。它不再解析 SpaceX/Efun 的凭据字段，也不再按卡台类型选择构造函数。

`CardPlatformRegistry` 负责构造和注册适配器。适配器实现已有 `CardPlatform` 接口，对外提供统一的产品、卡、余额、交易、开卡和加款模型。注册与构造本身不得发送请求或产生资金操作；实际能力仍由 `Capabilities()` 声明。

没有增加第二个数据库、队列或后台任务。原有付款开关、持久资金许可、交易快照和未知结果对账规则全部保留。

## 配置 key 与实现 kind

| 字段 | 含义 | 示例（仅示意） |
| --- | --- | --- |
| `key` | 一份具体卡台账号配置的稳定标识，也是库存、卡片账单绑定、资金意图使用的标识 | `cards-primary`、`cards-backup` |
| `kind` | 选用哪种适配器实现 | `spacexcard`、`efuncard` |
| `base_url` | 该配置对应的 API 地址，按适配器自己的规则校验 | 显式配置的服务地址 |
| `credential_encrypted` | 由共享加密配置保护的凭据 JSON | 不在文档或日志中填写真实值 |

工厂返回的 `ConfiguredCardPlatform.Key()` 是配置 `key`，`Kind()` 才是实现类型。两个配置即使共用一种适配器，也不能共用库存标识、卡 ID 空间或资金意图。

此前底层客户端的 `Key()` 固定返回类型名；直接把该客户端交给付款选号或资金意图执行器，会把同类型的不同配置混为一个标识。本次增加配置绑定包装器，修复这一点。默认配置 `key=kind=spacexcard` 的行为保持不变；包装器不修改卡台能力或任何资金请求。

若历史资金意图已把配置别名错误记录为 kind，本次不会自动改写或重新提交这些记录；应依据原订单、卡台和交易证据单独核对归属。没有执行任何数据库迁移。

为避免歧义，配置 key 接受 1–128 个 ASCII 字母、数字、点、下划线或连字符；kind 接受小写字母开头的小写字母、数字、下划线或连字符，最长 64 字符。注册时不能覆盖已存在的 kind。

## 当前内置适配器

| kind | 解密后凭据结构 | 已有能力契约 |
| --- | --- | --- |
| `spacexcard` | `appId`（可选）、`appSecret` | 开卡、加款、冻结；加款具备已有幂等契约 |
| `efuncard` | `apiKey` | 开卡、加款；不声明加款幂等，保留已有 5 分钟资金重放窗口 |

SpaceX 空地址继续使用原有默认端点。没有 `membership_card_platforms` 表或默认配置缺失时，原有 `membership_fulfillment_settings` 配置回退仍有效。未知的非默认配置不会回退到其他卡台。

实例每次单独构造，不按 kind 缓存客户端。凭据解析缓冲在构造后清理，配置对象默认格式化隐藏全部字段，JSON 序列化省略凭据和端点。构造错误只返回固定代码，不转发可能包含凭据的解析错误文本。

## 接入一个新卡台

1. 在 `internal/provider` 实现 `CardPlatform`，将上游字段归一化。底层客户端 `Key()` 返回自身 kind。
2. 提供 `CardPlatformFactory`：仅校验配置、解析凭据并创建客户端，不进行网络访问。客户端应保留自己需要的已解析字段，不保留传入的凭据字节切片。
3. 在 `NewCardPlatformRegistry` 的内置构造表增加一项。自定义组合根也可以创建 registry 并调用 `Register(kind, factory)`。这一步只涉及 provider 包；Processor 不需要新增 switch。
4. 给出真实能力契约。不能因为提供了 `RechargeCard` 方法就把 `RechargeIdempotent` 标为 true；未知扣款状态仍交由业务层对账。
5. 用同一个适配器的两个配置测试 key、端点、凭据和相同上游卡 ID 的隔离。补充响应格式变化、写后超时、幂等及账单资料契约测试后，再安排真实接入验收。

registry 是静态代码组合接口，不会下载或执行第三方插件，也不会把外部平台的 JavaScript 当作可信适配器。

## 验证与限制

新增测试通过虚拟 HTTP Transport 检查实际请求的端点和认证头，无外网调用。测试覆盖内置适配器选择、构造不发请求、同 kind 多配置隔离、重复/未知 kind、错误配置和错误脱敏；Processor 测试使用临时 SQLite，覆盖配置记录和旧设置回退。

这层只解决卡台接入边界。目标账号的登录、套餐结账、付款表单、银行验证、会员权益与取消续费由各自模块负责，不能用卡台构造成功或余额查询成功代替充值成功。
