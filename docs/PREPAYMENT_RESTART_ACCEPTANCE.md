# 付款前重复启动验收与六个后续节点

本页对应用户要求的“每一步重新启动多次复验”。先完成单条链路，排队、多路并发与更多卡台随后接入。这里新增的是可执行的本地合成浏览器验收，不修改生产付款许可，不创建第二套业务数据库或队列。

## 1. 新增的可执行验收

入口：

```sh
python3 scripts/verify-prepayment-restarts.py
```

CI 必须使用严格模式，不允许把缺浏览器或环境限制当成成功：

```sh
python3 scripts/verify-prepayment-restarts.py --require-browser --output /tmp/prepayment-restarts.json
```

默认使用已安装的 Playwright Chromium headless shell。已有完整 Chromium 时，可以在测试环境设置 `KWMEMBERSHIP_BROWSER_TEST_CHROME_PATH`。没有浏览器时不会自动安装；首次启动遇到已知环境限制会立即停止该序列，不重复撞同一限制。

| 退出码 | 含义 |
| --- | --- |
| 0 | 三次真实 Chromium 生命周期全部完成，所有断言通过 |
| 1 | 断言或运行失败；严格模式下浏览器不可用也属于失败 |
| 2 | 可选运行缺少浏览器或被环境阻止，验收不完整；离线契约测试可能已通过 |

机器结果包含 `expectedLifecycles`、`completedLifecycles`、逐轮证据、固定 blocker code，以及明确为 false 的真实账号、实际账单、付款提交标志。输出不包含卡资料、Session、实际付款 URL 或凭据。

## 2. 三轮真正关闭并重新启动

`python_executor/tests/test_browser_restart.py` 每轮都调用新的 `chromium.launch()`，新建 browser context 和页面；前一轮必须已经收到断开事件并关闭。不是在同一 browser 上刷新三次。

| 生命周期 | 表单变化 | 本轮材料变化 |
| --- | --- | --- |
| 1 | 卡号自动加空格，组合有效期自动格式化 | 独立合成姓名、地址、CVV、有效期与国家 |
| 2 | 月、年使用原生 select，接受规范化后的选项 | 第二组独立合成材料 |
| 3 | 普通组合有效期输入 | 第三组独立合成材料 |

每轮都执行以下验证：

1. 页面打开前 Cookie 和已存储 origin 为空。
2. 主页面、卡字段 iframe、外来 iframe 中 Cookie、localStorage、sessionStorage、旧任务 DOM 标记和输入值均为空。
3. 真实运行既有 `_fill_frames` 及 `FILL_FRAME_JS` 填表逻辑。主页面填写账单资料，卡 iframe 填写卡字段。
4. 用精确预期值检查姓名、地址、国家、邮编、卡号、有效期和 CVV；不会用“非空”代替“正确”。格式化字段按明确的预期表示检查。
5. 外来 iframe 的字段保持空白，写入计数为零。
6. 运行生产 `_checkout → _activate → prepare_action` 顺序；测试专用许可提供者在准备最终提交时拒绝，不能产生 action permit，不能调用实际 click，也不能报告 submitted。
7. 检查按钮 click、原生 submit 和 requestSubmit 计数都为零。
8. 本轮再模拟受控输入被页面清空，要求在申请付款许可前失败。失败后仍不点击或提交。
9. 在三个 frame 写入合成 Cookie、localStorage、sessionStorage 和 DOM 旧任务标记，确认写入真实发生，再关闭整个浏览器。下一轮必须看不到这些标记。

任一轮失败就停止，不通过继续重试掩盖失败。不接入实际卡台，也不调用账户或续费接口。

## 3. 网络与测试替身边界

所有页面使用 `checkout.fixture.invalid`、`card.fixture.invalid`、`foreign.fixture.invalid` 虚拟域，由 Playwright 在本地直接提供仓库内 HTML。没有请求真实 ChatGPT、OpenAI、Stripe 或卡台服务器，也不加载其 SDK。

页面请求只接受指定虚拟域、路径和 GET 方法；未知请求直接 abort，永不 continue。每个响应都有本地 fixture 标志，测试要求无未标记响应、无异常请求。WebSocket 被关闭，Service Worker 被禁止，浏览器使用关闭的本机回环代理作为额外出站阻断；页面 CSP 也禁止连接与表单外发。

生产填表 JS 和 Python 帧筛选都包含真实来源白名单。测试只在本进程中把来源常量替换成上述虚拟域；其余填表脚本保持逐字一致，生产文件与生产 guard 未修改。**这项测试不验证生产来源白名单**；白名单有原有的独立契约测试。

为了单独验证填表与付款前停止，`_wait_facts` 的服务端已验证页面状态是测试替身。它不证明真实结账选择器、Go 建单、计税、目标账号资格或付款许可已适配。测试用例以 Plus 形状的合成 lease 驱动既有状态机，不将合成材料中的 EG 国家选项写成“埃及 Go 已通过”。

## 4. 当前环境实际结果

2026-11-14（北京时间）在当前容器执行了入口：

- 四项离线契约测试通过：测试来源注入范围、未知请求终止、本地响应标志/WebSocket 阻断、生产 checkout 在许可拒绝后不点击。
- 默认 Playwright headless shell 未安装，返回 `CHROMIUM_NOT_INSTALLED`。
- 对本机已有 `/usr/bin/chromium` 做了一次独立尝试，启动被 `ProcessSingleton` 的 AF_UNIX socket 环境限制阻止，返回 `CHROMIUM_UNIX_SOCKET_DENIED`。
- 本机真实浏览器完成数为 **0/3**，入口退出码 **2**，状态 **incomplete**。

没有修改安全策略、IPC 权限或站点访问限制。三轮实际 DOM 结果须由具备正常 Chromium 环境的 CI 严格执行后补充，不能把本机的跳过结果写成三轮通过。

## 5. 登录之后的六个节点：顺序、所需证据与失败处理

登录恢复独立完成以后，以下节点按顺序推进。计划、套餐、卡台配置 key 与账号身份都要跟随同一个订单；不能用新建标签页数量代替隔离和证据。

| 节点 | 所需输入或凭据 | 通过依据 | 失败分类与停止条件 |
| --- | --- | --- | --- |
| 1. 账号资格与目标套餐 | 用户提供的有效会话、目标账号 ID/邮箱、目标套餐 | 新读取的指定账号与订阅状态一致，目标套餐可购买 | 会话拒绝、账号不符、资格不符分别停止；不得切到任意当前标签账号 |
| 2. 建立并核验结账 | 已确认账号、精确套餐建单适配器、价格契约 | 取得目标账号的结账；真实页面套餐、币种、小计/税费/合计与契约一致 | 未知 SKU、缺失金额、价格变化、未识别页面停止；Go 未实现的自动建单保留明确缺口 |
| 3. 卡台与卡材料准备 | 卡台配置 key、合法卡台 API 凭据、产品/卡 ID、发卡资料 | 同一卡片的资料、余额、账单信息及资金操作结果有依据 | 不支持能力、余额不足、资料缺失、开卡/加款结果未知分别停止或对账；不盲目重复资金请求 |
| 4. 填表与付款前复核 | 本订单结账、同一卡片材料、支持的页面/iframe | 精确回读、有效性检查、账号/套餐/最终金额再次一致，提交仍未发生 | 输入重置、frame 失效、未知必填项、控制变化停止；本轮重复浏览器测试覆盖其合成 DOM 机制 |
| 5. 付款提交与持卡人验证 | 明确付款授权、持久化动作许可、提交前卡交易基线 | 每个推进/最终动作跨过许可记录；响应保存为已提交、需验证或结果未知 | 许可拒绝不点击；3DS/银行验证交接用户；提交后超时进入未知结果核验，不能换 tab 重付 |
| 6. 交易/权益核验与续费 | 新卡交易、指定账号权益观察、订单的续费要求 | 交易与会员权益对应；若要求关闭续费，则操作后重新读取确认关闭 | 只有扣款或只有页面成功不能结束；权益延迟、状态冲突、取消结果未知分别保留待核验状态 |

第 3 节点通过统一卡台接口接入，不把某一家卡台的认证格式散布到建单或浏览器代码。第 5、6 节点不能靠反复提交来提高“通过率”。只有尚未产生资金动作的纯观察、页面定位和填表，才适合有界重新启动复验。

## 6. 真实站点后续验收记录

每个节点记录版本、环境、合成/真实范围、尝试次数、明确状态码及脱敏证据。至少区分：

- `implemented`：已有代码。
- `fixture_verified`：本地合成材料通过。
- `browser_fixture_verified`：正常 Chromium 上通过，包括明确次数。
- `live_verified`：允许环境中的真实账号/页面完成对应节点。
- `blocked`：列明缺失凭据、未支持适配或访问限制。

真实账号与卡数据不进入仓库、日志或 CI。CI 只运行本页的离线合成页面验收。付款暂停期间，真实站点验证最多停在获准执行的付款前边界；绑卡、开卡、加款、提交付款及改变续费都分别按既有授权与实际访问能力处理，不用 fixture 的成功代替这些业务结果。
